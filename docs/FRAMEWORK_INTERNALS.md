### Test Data Files — per suite

| File | Purpose |
|------|---------|
| `test-data/ado-cases-pod3-{suiteId}.json` | All test cases fetched from ADO (id, tcTag, title, steps) |

## How It Wires Into Every Test

Every spec calls `useSuiteAnnotations()` once inside the describe block:

```typescript
import { test, expect, useSuiteAnnotations } from '@fixtures/tc-fixture';

test.describe('Suite 18178 — API First Rule Integration', () => {
  useSuiteAnnotations('18178', '14019');   // suiteId, planId

  test('[TC-AI-001] @TC17340 Verify creating a rule...', async ({ request }) => {
    // test body
  });
});
```

`useSuiteAnnotations()` registers a `test.beforeEach()` hook. Before every test it automatically stamps four annotations on `test.info()`:

| Annotation | Description | Example |
|------------|-------------|---------|
| `TestCaseID` | Human tag extracted from `[TC-xxx]` in test title | `TC-AI-001` |
| `ADO_CaseID` | ADO work-item numeric ID resolved from tags/JSON | `17340` |
| `ADO_SuiteID` | Suite ID passed to `useSuiteAnnotations` | `18178` |
| `ADO_PlanID` | Plan ID passed to `useSuiteAnnotations` | `14019` |

### ADO_CaseID Resolution (highest → lowest priority)

```
1.  @TC17340 Playwright tag embedded in test title     ← most explicit
2.  tc-map-pod3-{suiteId}.json explicit map entry
3.  Direct numeric parse from TC-17461 format
4.  ado-cases-pod3-{suiteId}.json lookup by tcTag
5.  ado-cases-pod3-{suiteId}.json lookup by title substring
```

│    → reads all test annotations                                  │
│    → parses console stdout for API call logs (→ / ←)            │

│    → writes test-results/ado-tc-report.json                     │

│    → for each suite:                                             │
│        GET  test points        (caseId → pointId map)            │

# PostgreSQL DB Setup

## Where Credentials Live

| Variable | File | Notes |
|----------|------|-------|
| `DB_HOST` | `.env.qa` / `.env.staging` | Environment-specific |
| `DB_PORT` | `.env.qa` / `.env.staging` | Defaults to `5432` if absent |
| `DB_NAME` | `.env.qa` / `.env.staging` | Environment-specific |
| `DB_USER` | `.env.qa` / `.env.staging` | Environment-specific |
| `DB_PASSWORD` | `.env` (base, shared) | Supports encrypted `ENC:<iv>:<tag>:<cipher>` format |
| `ENCRYPTION_KEY` | `.env` (base, shared) | 64-char hex — AES-256-GCM key for decrypting DB_PASSWORD |

`.env.qa` / `.env.staging` are loaded automatically by `src/core/config/env.ts` based on `TEST_ENV`.

## The Two Pool Implementations

### Modern — `src/db/client/pool.ts`

Singleton pattern. The pool is created once and reused for the whole test session.

```typescript
import { query, closePool } from '@db/client/pool';

// Use anywhere — no setup needed
const rows = await query<{ id: string }>(
  'SELECT id FROM rules WHERE status = $1',
  ['ACTIVE']
);

// Call once in globalTeardown
await closePool();
```

- Max 5 connections
- 30 s idle timeout, 5 s connection timeout
- Password goes through `resolveSecret()` — handles `ENC:...` encrypted format

### Legacy — `src/core/utils/db.ts`

Per-query client checkout. Suitable for `beforeAll` / `afterAll` hooks.

```typescript
import { dbQuery, dbInsert, dbCleanup } from '@utils/db';

// SELECT
const rows = await dbQuery<{ rule_id: string }>(
  'SELECT rule_id FROM rule_config WHERE suite_id = $1',
  ['18178']
);

// INSERT test data
await dbInsert('test_rules', { name: 'Test Rule', status: 'DRAFT' });

// DELETE after test
await dbCleanup('test_rules', 'name = $1', ['Test Rule']);
```

- Max 10 connections
- Each call checks out its own client and releases it
- Does not use `resolveSecret()` — use only with plaintext passwords

## How to Add a DB Prerequisite to a Test

Change the import in the spec from `@fixtures/tc-fixture` to `@fixtures/test`, then use `db` in `beforeAll` or inline:

```typescript
import { test, expect, useSuiteAnnotations } from '@fixtures/test';

test.describe('Suite 18178', () => {
  useSuiteAnnotations('18178', '14019');

  // Run a DB check before the whole suite
  test.beforeAll(async ({ db }) => {
    const result = await db.query(
      'SELECT COUNT(*) AS cnt FROM rules WHERE status = $1',
      ['ACTIVE']
    );
    const count = Number(result.rows[0].cnt);
    if (count === 0) {
      throw new Error('Prerequisite failed — no ACTIVE rules found in DB');
    }
  });

  // Use DB inline for a specific test
  test('[TC-AI-001] @TC17340 Verify rule creation', async ({ request, db }) => {
    const [config] = await db.query<{ base_url: string }>(
      'SELECT base_url FROM env_config WHERE env = $1',
      ['qa']
    );
    // use config.base_url as dynamic prerequisite
  });
});
```

## Environment Loading Flow

```
TEST_ENV=qa (in .env)
      ↓
env.ts: loadEnv()
      ↓
  1. dotenv.config()           loads .env
  2. dotenv.config(.env.qa)    overlays environment-specific values
      ↓
DB_HOST, DB_PORT, DB_NAME, DB_USER  ← from .env.qa
DB_PASSWORD                          ← from .env (shared)
ENCRYPTION_KEY                       ← from .env (shared)
      ↓
pool.ts: resolveSecret(DB_PASSWORD)
      ↓
  if value starts with ENC: → decrypt with ENCRYPTION_KEY
  else                      → use as-is
```

To encrypt a DB password:
```bash
npm run encrypt:creds -- --value "yourpassword"
# Outputs: ENC:<iv>:<authTag>:<ciphertext>
# Paste that into .env as DB_PASSWORD=ENC:...
```

# Trace Viewer

## Configuration in `playwright.config.ts`

```typescript
use: {
  screenshot: 'only-on-failure',   // screenshot saved when test fails
  trace:      'on-first-retry',    // trace zip saved on first retry
}
```

Video recording is intentionally disabled — trace viewer captures everything video does and more.

---

## What `on-first-retry` Means

A trace is recorded only when a test **fails and Playwright retries it** (retry attempt 1). If the test passes first time, no trace file is created — keeping disk usage minimal during clean runs.

Retry behaviour is controlled by:
```typescript
retries: process.env.CI ? 1 : 0
```

| Environment | Retries | Trace saved |
|-------------|---------|-------------|
| CI | 1 | Yes — on the retry attempt |
| Local | 0 | Never (no retries = no first-retry) |

---

## The Four Trace Modes

| Mode | When trace is saved | Best for |
|------|---------------------|----------|
| `on-first-retry` | Retry attempt #1 only | CI — current setting |
| `on-all-retries` | Every retry attempt | Flaky test investigation |
| `retain-on-failure` | Every failed test, no retry needed | Local debugging |
| `always` | Every test pass or fail | Heavy debugging — high disk use |
| `off` | Never | Disable completely |

---

## What a Trace Contains

| Captured data | Detail |
|---------------|--------|
| DOM snapshots | Full page state before and after every action |
| Network log | Every request and response — URL, headers, body, status, timing |
| Console logs | All `console.log`, warnings, and errors |
| Screenshots | Screenshot at each step automatically |
| Action timeline | Scrollable timeline showing exact execution order |
| Source location | Which line of test code triggered each action |

This is why video is not needed — the trace is strictly more informative.

---

## Where Traces Are Saved

```typescript
outputDir: 'test-results/'   // in playwright.config.ts
```

Trace file path:
```
test-results/{test-name}-{project}/trace.zip
```

---

## How to Open a Trace

**CLI (fastest):**
```bash
npx playwright show-trace test-results/<test-name>/trace.zip
```

**Drag and drop:**
Open [trace.playwright.dev](https://trace.playwright.dev) in a browser and drag the `.zip` file onto the page. No installation needed.

**From the HTML report:**
Run `npm run report` to open the Playwright HTML report. Any failed test has a **Traces** link that opens the viewer inline.

---

## Enabling Traces Locally for Debugging

The current `on-first-retry` setting never saves traces locally because `retries = 0` on local runs. To capture traces locally when debugging a failure, temporarily change the config:

```typescript
// playwright.config.ts
trace: process.env.CI ? 'on-first-retry' : 'retain-on-failure',
```

This saves a trace for every local failure without affecting CI behaviour. Revert before committing.

---

## Trace Viewer vs Screenshot vs Video

| | Screenshot | Video | Trace Viewer |
|--|-----------|-------|-------------|
| DOM snapshot per step | No | No | Yes |
| Network requests | No | No | Yes |
| Console logs | No | No | Yes |
| Timeline scrubbing | No | Basic | Yes — precise |
| Source code link | No | No | Yes |
| Disk usage | Low | High | Low (compressed) |
| Current config | `only-on-failure` | Disabled | `on-first-retry` |
